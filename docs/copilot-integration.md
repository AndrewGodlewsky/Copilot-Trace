# Copilot desktop integration

This guide extracts reusable lessons from the source revision recorded in [transfer decisions](context-transfer.md). Concrete API names were checked against installed SDK build `1.0.106-8.unstable.r43566476370.g869eef3` during setup. This experimental surface can change: inspect the installed declarations before changing integration. Historical runtime observations below are not a compatibility guarantee.

## Runtime and plugin layout

The implemented shell uses plain ES modules and local HTML/CSS/JavaScript, with no bundling step or npm dependency. `extension.mjs` imports `createCanvas` and `joinSession` from the host-provided `@github/copilot-sdk/extension`, registers the canvas, and releases it on shutdown. The installed `extension.d.ts`, `canvas.d.ts`, `types.d.ts` and `generated/rpc.d.ts` are the API reference.

The root Agent Plugins 1.0 `plugin.json` describes Trace; `.github/plugin/marketplace.json` lists it; `com.github.copilot/extensions/trace/` supplies the runtime extension; `skills/trace/SKILL.md` launches it. This is the plugin-packaged layout used by the reference, distinct from standalone repository/user canvas folders. GitHub's [canvas documentation](https://docs.github.com/en/copilot/how-tos/github-copilot-app/working-with-canvas-extensions) describes the native surface and common extension structure.

Tests accept `COPILOT_SDK_DIR` (directory containing `index.js`) and `COPILOT_CLI_PATH` (installed executable). These are explicit development selections, not production discovery. Never hardcode a cache build directory or a path to the reference checkout into shipped behavior. Do not launch `extension.mjs` using ordinary Node and mistake a missing host SDK for a reason to install an npm substitute.

During this setup, the successful executable was `copilot.exe` adjacent to the selected `copilot-sdk` directory under the installed `github-copilot-sdk/cli` cache. The lower-level `copilot/pkg/.../prebuilds/win32-x64/copilot-runtime.exe` rejected session creation with "No extension launch provider is registered for standalone extensions". Select the extension-capable installed launcher, not just an executable with a similar version. Keep the exact machine paths in local environment settings.

## Canvas lifecycle

The host's canvas catalog supplies provider identity. `createCanvas` binds `open`, `onClose` and any declared actions. Reopening an existing instance focuses that panel; rendering reload and creating a new instance are separate concepts.

Trace checks the attached session identity, shares one startup promise per instance, gives separate instances separate tokenized servers, and closes pending or active servers on close/shutdown. A new open after close gets a new capability URL. The panel has no action API. Its browser module polls a protected read-only snapshot once per second; unchanged revisions return HTTP 304.

For future actions, define bounded input schemas and validate runtime data. Bind asynchronous results to session, instance and request identity, plus any user-input revision that makes the result valid. Timeouts and UI cancellation do not themselves prove a worker stopped. Reject late results and preserve user edits.

## Loopback security

Implemented: bind `127.0.0.1`, use an unpredictable per-instance capability path, require exact Host, allow only known static assets and the read-only events endpoint, reject non-read methods and apply restrictive CSP, no-store, no-sniff and no-referrer headers. Assets are read from packaged paths, never arbitrary request paths.

When writes are added, require exact Origin and an intentional client marker, validate content type, enforce byte limits before parsing JSON, and authorize each operation. A local port alone is not authorization. Keep capability URLs, prompts and credentials out of error messages and support exports. Render untrusted text literally; sanitize any deliberately supported markup and validate link schemes.

## Recorded session evidence

Each canvas instance subscribes with `session.on(handler)` before calling `getEvents()`. History and buffered live entries reconcile by event ID, ignoring checkpoint copies. Retained records sort by recorded timestamp before trimming, so ephemeral live events remain between their persisted neighbors. Ties keep insertion order; missing/invalid timestamps appear last with a visible unknown time. History failure or a ten-second timeout leaves live collection active and displays a warning. Closing unsubscribes without disconnecting the host-owned session.

`trace.mjs` projects supported event types into bounded text records; it retains at most 300 events and 12,000 UTF-16 code units of evidence per event. The SDK history call itself can materialize the full chat history. This proof of concept skips token deltas and internal canvas events, so it is not a lossless trace. No plugin transcript files are written.

Skill `trigger` is observed attribution, not proof of a causal instruction. Tool start/result correlation uses both agent identity and tool-call ID. The event envelope's `parentId` is chronological linkage, not causality. Render all evidence with `textContent`; no event content is interpreted as HTML or a URL. Encrypted and opaque reasoning fields are omitted. New event fields require checking the installed declarations.

Request chapters inspect `UserMessageData.delivery` (`idle`, `steering`, `queued`) and the optional `interactionId` shared with `AssistantTurnStartData`. These fields were checked in the installed build named above. Delivery describes loop timing, while message origin is a separate `source` field: a user-role record is not necessarily human-typed input. `idle` starts its own run; steering arrives within an active run; queued input is consumed as its own run afterward. A queued message alone is not evidence that earlier work ended. Loop `turnId` values can repeat across requests and cannot replace interaction identity. Project only recognized delivery values and exact bounded interaction IDs; older or malformed records remain unknown. Chapter membership describes a retained chronological interval, not a causal parent for its neighboring or interleaved-agent events.

The installed-runtime fixture first proves that opening and observing Trace makes zero model requests. Its separate input phase sends three synthetic prompts to a fixed-response loopback provider in the same disposable session, then checks the attached extension's delivery/interaction projections against actual host events. The inspected runtime reported the requested immediate-mode input as queued, so presentation uses recorded delivery rather than assuming send-mode semantics. This fixture establishes actual idle/queued metadata and interaction linkage; synthetic unit cases cover steering and malformed/partial histories. It does not establish paid-provider behavior, native rendering or real model quality, and it never uses an existing user session. See [prompt chapters](prompt-chapters.md) for the supported grouping and fallback rules.

The installed `generated/session-events.d.ts` defines matching `turnId` fields on `AssistantTurnStartData` / `AssistantTurnEndData` and matching `hookInvocationId` on hook start/end. Project these identifiers intact (maximum 256 characters; reject oversized identifiers rather than clipping into false matches). Turn indentation represents only the recorded same-agent interval, never a causal parent. Keep interleaved agents in timestamp order; unknown starts, mismatched ends, idle/unknown-delivery user input and aborts stop inferred intervals. Validated steering or queued input preserves an observed same-agent interval without nesting the input itself; it does not prove that work finished. Session-level notices stay outside intervals. Statistics pair consecutive turn boundaries per agent and turn ID; each later start counts separately because loop IDs need not be session-unique. Hooks and tools deduplicate by agent plus their invocation ID; skill loads count `skill.invoked` events. `invokedAtTurn` is a projected chat-message count, not a model turn ID, and is not used for grouping. All counts describe only the retained window, including partial calls; unidentifiable events are disclosed separately.

Agent lanes use the inspected `SubagentStartedEvent` envelope's optional `agentId` as source identity, and `SubagentStartedData.toolCallId` as the explicitly recorded spawning tool invocation. Completion/failure data expose the same invocation field; `SubagentCompletedData.cancelled` distinguishes cancellation from an ordinary completion record. Display names are not identities. The envelope's `parentId` remains a chronological predecessor; the distinct optional `data.parentId` is a spawning task-registry identifier. In the nested fixture described below, it matches the spawning agent's envelope identity. This observation does not make arbitrary IDs equivalent: require consistent explicit invocation/source evidence and leave missing or conflicting relationships unknown. See [agent lanes](agent-lanes.md) for timing, identity and fallback rules.

The installed-runtime fixture's second disposable session initializes an exact allowlist containing only `task` and explicitly configures a synthetic agent with no tools, skills or MCP servers. Four fixed loopback responses produce two distinct agent IDs sharing a display name, recorded start/completion overlap, matching spawning invocation IDs and child-turn `parentToolCallId` values. The attached Trace snapshot and handoff helper are compared with actual raw task arguments, lifecycle boundaries and returned parent-tool text. Reported `durationMs` can differ from the boundary timestamp interval, so the presentation must distinguish reported durations from observed intervals. No real model inference or existing user session is used.

The seventh disposable session adds five fixed responses for main-to-middle-to-leaf delegation and the two returns. Main and middle expose only the `task` descriptor; the leaf has no tools, and permissions are denied. The two agents share a display name but have distinct source IDs. Each exact parent invocation retains its own literal Unicode/markup prompt and distinct returned text, verified against the joined Trace snapshot and handoff helper. The leaf's `data.parentId` matches the middle source, while its child-turn `parentToolCallId` matches the middle's task call. Failure, cancellation, partial history and malformed/conflicting relationships remain schema-based cases. The complete fixture makes twenty fixed local responses across seven owned sessions.

Handoff details use complete identity-matching retained evidence and known task arguments, not private child-session queries. The parent tool's `result.content` is returned text; a subagent completion reports lifecycle and does not itself supply that body or prove task correctness. Missing or clipped content is not reconstructed. Explicit parent links identify delegation without proving which instructions, files or parent messages the separate child context received. Trace does not spawn or control agents. See [delegation handoffs](delegation-handoffs.md).

Action stages inspect `AssistantMessageData.toolRequests`, `PermissionRequestedData.requestId` and nested `permissionRequest.toolCallId`, `PermissionCompletedData.requestId` / `toolCallId` / `result` / optional `decisionSource`, and tool boundary IDs. Correlate only complete retained evidence with exact source and call/request identity. Permission recovery fields `ownerSessionId` and `ownerAgentId` require an ownership mapping that the panel snapshot does not supply; their records remain separate. An absent decision never establishes preauthorization, and a result kind mentioning a user does not prove a human decided. See [action stages](action-stages.md) for supported kinds and fallback cases.

Two additional installed-runtime fixture sessions allow only `powershell`. Three fixed local responses request a write to an owned disposable file: the fixture's owning client returns `reject` or `approve-once`, the denied write creates no file, and the approved write produces the fixed text. Both paths emit `tool.execution_start` **before** permission evaluation, so a start means invocation entry, not proof that the underlying operation ran. Trace itself issues no permission decisions. The owning client observes the permission request, while the joined Trace observer receives the proposal, invocation, decision and result live. Holding the decision open did not make the request appear in that live stream. Reopening a panel hydrates the request from history with `ownerSessionId`; without a verified mapping in the snapshot, its permission links remain unknown and the original evidence stays accessible. The fixture verifies these distinct live/history paths, exact original links and unknown permission while a decision is pending. Fully linked requests, cancellation, preauthorization without retained evidence and malformed/ambiguous histories have schema-based unit coverage. These observations describe the inspected runtime, not a universal host sequence.

Hook boundaries expose `hookInvocationId`, `hookType`, optional input/output and reported success/error. The installed `SessionHooks` declarations distinguish `postToolUse` after successful results from `postToolUseFailure` after failure; unknown types have no inferred timing. A hook event records a pipeline point, not proof that a configured script ran. The fifth runtime-fixture session registers only three callback types and observes five callback calls but nine pipeline invocations and eighteen boundary events, including lifecycle types with no registered callback. One pre-tool pipeline covers two tool requests; its output omits the callbacks' context while both post-tool results expose their fixed context. Trace retains the exact source, invocation ID, time and raw data. Counts describe retained pipeline identities, not callback or script counts. The plugin adds no hooks, configuration reads or permission decisions; callbacks belong only to the disposable test session. See [hook lifecycles](hook-lifecycles.md).

`SkillInvokedData` exposes the loaded instruction `content`, recorded `name`, `path` and optional `trigger`/`arguments`/source metadata. The path may be empty for an SDK-provided skill. The fifth fixture session supplies in-memory skills with `enableSkills: true` (empty mode otherwise disables skills), explicitly invokes one through `commands.invoke` and sends its returned prompt to the fixed local provider. Its event contains the exact instruction body and `user-invoked` trigger but omits optional invocation arguments, even though the returned prompt contains them. Changing the fixture source after loading does not change Trace's retained evidence or cause another skill read. Product code must never invoke a command or read a path to fill missing historical content. A loaded body does not prove compliance or referenced-script execution. Preview complete identity-matched retained evidence only; clipped JSON cannot be reconstructed from the current file. See [skill instruction evidence](skill-instructions.md).

The installed `session.rpc.instructions.getSources()` contract returns source IDs, labels, source paths, current content, category, location and optional applicability/default-disabled metadata. Its description calls these loaded sources in merge order, but disposable runtime probes establish narrower evidence: a conditional source can be listed with its full body while that body is absent from the actual model request; changing a source file after a turn changes a later API response without another model request. Explicit organization guidance can reach the model yet be absent from this list. A nested-agent source can be a generated index rather than the referenced instruction body. Catalog inclusion therefore does not establish historical loading, completeness, load time or compliance. Missing applicability is unknown, `defaultDisabled` is not current enabled state, and reported order is not a complete precedence hierarchy.

Trace requests this main-session snapshot only on explicit refresh through the protected `instruction-sources` endpoint. It projects bounded fields and content with an aggregate response budget, records retrieval time, and keeps this current catalog separate from retained `skill.invoked` load evidence. It does not call `instructions.reload()`, sessionless discovery, filesystem inspection or prompt/model operations. Unsupported or failed reads do not stop event collection. Current source content must never replace a historical skill body. See [instruction sources](instruction-sources.md) for limits, lifecycle handling and supported states.

The fifth installed-runtime fixture adds explicit disposable `instructionDirectories` with global and conditional files, plus in-memory organization guidance. Empty mode, disabled ambient discovery and an owned home/project remain in use; `skipCustomInstructions: false` opts only the fixture into instruction loading. The fixed provider inspects what actually reached its request, while Trace endpoint reads verify the current catalog before and after an owned file change. These checks keep historical skill evidence intact and add no model, MCP or skill-provider calls. They establish the observed API distinctions on this installed runtime, not a full historical instruction hierarchy or proof of obedience.

The retrieval ledger uses the inspected `ToolExecutionStartData.arguments`, exact same-agent call identity, and `ToolExecutionCompleteData.success` / `result.content`. The latter is the recorded concise model-facing text and may itself be shortened by the host. `detailedContent` is for timeline display and can contain formatted diffs; its presence or length does not establish complete retrieval or delivery to the model. Recognizing a supported request contract does not establish its native implementation origin. Trace never reads a recorded path or contacts a recorded URL to fill gaps. See [retrieval ledger](retrieval-ledger.md).

The sixth disposable runtime session allows only `view` and `grep`, with read permission limited to three exact owned paths and three fixed call IDs. Two fixed local responses produce a successful requested line-range read, a successful two-line search excerpt and a failed missing-path read. All six boundaries are checked against the joined Trace snapshot. The failed result contains diagnostic text, so text alone cannot prove successful retrieval. The fixture knows its file has thirty lines, but that private fixture knowledge is not available to the ledger and must not become a coverage denominator. No external retrieval or user project is accessed.

The installed `CompactionStartData` and `CompactionCompleteData` contracts expose optional `compactionAttemptId`, `summaryContent`, before/after context-token counts and an accounting basis. Trace pairs complete matching evidence by exact source and attempt ID; missing, duplicated or conflicting boundaries cannot acquire a relationship from chronology. The summary is reported model-generated text, not a complete context view or proof that meaning was preserved. The installed `ToolExecutionCompleteContentShellExit` contract supplies `outputTruncated` for its optional `outputPreview`. A true value establishes an incomplete preview, not the amount omitted or completeness of a separate text field. The browser can read snapshots only with the capability URL and exact Host. Supplied Origin must match the loopback origin; cross-site fetch metadata is rejected. CSP permits only same-origin script/style/connect/img. An endpoint connection does not prove every host event is available.

## Model operations

These are future design options, not implemented features:

| Path | Ownership and constraints |
| --- | --- |
| Attached-chat request | Use only when the product explicitly needs the user's existing conversation. Explorer used `send({ mode: 'enqueue' })`. Keep model selection, billing and permission decisions with the host. Correlate callbacks; cancelling the plugin request cannot be claimed to cancel that chat turn. |
| Plugin-owned helper | Create a new isolated client/session with a disposable workspace/configuration, an explicitly bounded input and its own cancellation/accounting. Stop only owned work. Keep its conversation out of unrelated sessions. |

Before helper inference, verify the host-paired runtime, signed-in account identity, eligible Copilot catalog model, actual helper workspace and initialized tool metadata. Read the parent model; do not change it. Recheck identities/model after startup where needed. Honor managed settings and model policy. Fail visibly if prerequisites do not hold; do not silently switch provider, model or account.

For a tool-free transformation, disable ambient config/instruction/skill/plugin discovery and MCP tools, deny tool/permission hooks, initialize tools and require exactly zero actual tools. For web-enabled work, see [tool discovery](#tool-discovery). Explicitly load any curated plugin instructions rather than relying on ambient discovery.

Capture the exact prompt and instructions once, measure their UTF-8 byte budget, include complete records or report omissions, and pass those same strings to the helper. Track freshness for the actual transmitted data; unrelated edits should not invalidate a result. Validate strict model output before exposing it. Separate proposals from saved user decisions whenever the feature requires review.

Set overall and phase deadlines, bound tool use, and wait for actual worker release before reusing a single-operation slot. Retain and deduplicate minimal usage receipts before removing the temporary session. Usage records may include operation/model/token/credit status and accounting IDs; omit prompts, results, credentials and account names. When shutdown or accounting is uncertain, retain recovery evidence and report uncertainty; do not retry inference automatically. Use Trace-owned data paths and labels.

## Tool discovery

Trace's provenance display uses complete retained invocation evidence, with no discovery RPC. The inspected `ToolExecutionStartData` exposes `mcpConfigServerName`, `mcpServerName`, `mcpToolName`, optional `mcpServerDisplayName`, `mcpConfigSource` and `mcpTransport`. The explicit configured key resolves legacy ambiguity: older `mcpServerName` values could be display names. Configuration source `plugin` or `builtin` describes where an MCP configuration came from, not a native tool implementation's origin. A tool result inherits provenance only from its unique validated retained start. See [tool provenance](tool-provenance.md).

`tools.getCurrentMetadata()` reads currently initialized metadata; it does not establish historical invocation origin. In a disposable probe, two reads made no additional MCP requests or inference. `getBuiltinDescriptors({})` materialized built-in contracts even when the offered set contained only MCP tools. A second session registered a custom `powershell` with the documented `overridesBuiltInTool: true`; current metadata had no origin discriminator while the built-in descriptor still existed. Neither name intersection nor missing MCP fields proves built-in or plugin origin. Trace keeps these cases unknown and avoids initializing tools or querying a current inventory for historical badges.

The optional capability comparison reads `session.rpc.tools.getCurrentMetadata()` and `session.rpc.skills.list()` through the joined session. A user-requested protected `capabilities` snapshot records retrieval time and main-session scope. Tool metadata can be uninitialized (`tools: null`); skill entries report `enabled`, `userInvocable` and source, but omit `disableModelInvocation`, so model invocation availability stays unknown. The runtime fixture supplies both an ordinary skill and a manual-only skill whose returned catalog flags are identical. Repeated actual Trace endpoint reads before and after observed activity make no additional MCP requests, skill-provider reloads, body reads or inference requests. Discovery failure does not stop event collection. See [capability inventory](capability-inventory.md) for bounds, identity matching and stale/partial states.

The comparison never initializes tools, starts servers, reloads skills or infers capability availability from installed plugins. In particular, `mcp.list()` may start or wait for servers, and `mcp.listTools()` makes live requests; neither is used. Current main-session metadata cannot prove past availability or child-agent scope. An available item absent from retained activity is only not observed in that window.

The installed-runtime fixture's fifth session explicitly configures two owned HTTP MCP endpoints with the same raw tool name and title. Session creation initializes those fixtures; subsequent metadata reads and opening Trace add no MCP requests or inference. Two fixed loopback model responses invoke both tools and produce successful results. The attached snapshot preserves each distinct configured server key and its exact call identity. These observations establish the MCP path on the inspected runtime; synthetic fixtures cover optional display names, metadata changes, malformed/unknown fields and unsupported attribution. MCP identity alone does not prove a network request or successful external effect.

The source's November 16 investigation found built-in `web_fetch` and GitHub MCP `web_search` had different origins. The observed runtime required configuration discovery for built-in GitHub MCP injection and skipped injection for a custom provider. These gates require revalidation on the installed runtime before adoption.

- Source-qualified allowlists were `builtin:web_fetch` and `mcp:web_search`; `builtin:web_search` was incorrect.
- `githubMcpToolConfig.additionalTools: ['web_search']` requested search; it did not restrict all other tools by itself.
- Run `session.rpc.tools.initializeAndValidate()` then `getCurrentMetadata()` before inference. Validate actual names and origins, including `github-mcp-server/web_search` and MCP server/tool identity. Initialization needs no paid bootstrap prompt.
- `mcpServers: {}` alone did not disable discovered MCP servers. If discovery is needed, use an empty disposable config directory and workspace, explicit feature opt-outs and verification of the resulting tool set.
- Grant only the intended operation's permissions. Revalidate redirects/public URL eligibility, and preserve managed human-approval and sandbox-bypass boundaries.
- Successful fetch hooks establish that a page was accessed, not that its claims are true. Keep sourced evidence distinguishable from model reasoning.

The local custom-provider fixture in Explorer established readiness/filtering behavior, not live GitHub MCP entitlement. Trace's current smoke fixture does not test these optional helper APIs.

## Storage and project context

Future persistence should use a dedicated Trace namespace (for example `COPILOT_HOME/plugin-data/trace`) and keep shared user artifacts separate from private drafts, session bindings, preferences, locks, recovery and usage records. Imported session IDs and paths must not confer authority. Validate an allowlisted document schema, preserve Unicode and use atomic replacement, serialized writes and revision/digest checks against overlapping writers. Keep the last valid document recoverable after failed saves.

For authorized project access, use fresh `session.rpc.metadata.snapshot().workingDirectory`; the source found `session.workspacePath` was an artifact location, not the project root. Verify local/current session metadata. Select and bound files explicitly, exclude secrets by default, and validate canonical roots, ancestor/file identity and links before and after reading. A stored path is not fresh read permission. Treat excerpts as untrusted data and show the actual selected context; avoid retaining it in exports, receipts or prompts for unrelated operations. Native runtime logs can retain content even when plugin storage does not.

If a future feature reads a formatting template, separate that contract from general project context: read the explicitly chosen file, validate and retain only the structure needed for formatting, and discard examples/body/metadata values. Keep only a bounded relative reference and hash for provenance; that reference grants no future read permission. This extracts the general lesson from Explorer's ADR-template rule without adding an ADR feature.

Delete only verified plugin-owned paths. Protect active worker data, retained recovery evidence and the last good saved version. User-visible limits must distinguish bytes from JavaScript UTF-16 lengths and token estimates.

## Diagnostics and native limitations

Readiness checks should inspect prerequisites without starting inference, recording audio, downloading models or modifying host settings. Report `ready`, `unsupported`, `unavailable` or `unknown` accurately; a cache folder name or version stub is not authoritative desktop-version evidence. Project a small support schema from safe fields instead of dumping arbitrary objects and redacting afterward.

Explorer observed that native composer dictation was not automatically available inside a guest canvas. It also found that a child `fork()` under the host's single-executable runtime did not behave like ordinary Node; its voice adapter used an installed bootstrap. Preserve these as reasons to investigate before adopting voice or subprocess code, not reasons to copy its adapter. Trace implements neither.

The reference project's canvas-icon investigation found that desktop 1.4.2 resolves the native tab icon from the owning plugin's session inventory metadata. The root manifest's `extensions.com.github.copilot.logo` supplies a compact SVG; a canvas-level icon override and page favicon do not repair missing plugin metadata. Live local marketplace installs sometimes omitted it, while a managed cached installation restored it. Trace uses `assets/trace.svg` in that manifest and serves the same file in its panel header and favicon.

The installed CLI also accepts a validated local package directory and creates a managed cached install. A disposable-profile fixture verified Trace's exact SVG bytes in that cache and exercised its runtime. This establishes packaging and installation, not visible tab rendering: confirm the native tab after restarting the desktop app.

## Installation and distribution

Use the Copilot CLI rather than modifying host databases. Marketplace registration, plugin installation, enablement and new-session discovery are separate steps. Local marketplaces retain a live dependency on the checkout. `install:copilot` registers that live development setup; installing a packaged local directory directly creates a managed cached preview. Reinstall updated packages for new versions. A cached GitHub marketplace install is the intended distribution route once this repository is published and validated.

The inspected CLI warns that direct local-path installation is deprecated for a future release. Use it only for these validated previews; move to the cached GitHub marketplace for ongoing distribution.

Ship runtime code, web assets, launch skill, logo and release notes together. Keep all current version references synchronized. CLI/plugin-list success proves registration, not visible rendering. Unit tests, installed-runtime fixtures, manual UI acceptance and live account/model quality answer different questions; report each separately.
