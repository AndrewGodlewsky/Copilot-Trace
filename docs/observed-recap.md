# Observed recap

The footer’s **Recap** control opens an optional factual summary of captured events. Choose the entire retained range or a supported chronological request interval. Nothing is selected automatically. The choices, bounds and contents freeze when the dialog opens; close and reopen to capture current evidence. The recap stays in memory and is discarded on close, mode changes or page teardown. It does not create a saved report or send a model request.

Request intervals reuse [prompt chapters](prompt-chapters.md): main-chat idle input begins an interval, an unambiguous queued interaction begins at its later main turn, steering stays inside the interval, and an interruption ends it. An earlier queued prompt can appear as linked boundary context outside the interval; it does not enter that interval’s counts. Unsupported boundaries remain unknown, with the full retained range available as an explicit fallback. Neither a turn end nor an assistant answer establishes request completion. Intervals describe recorded order, not ownership of overlapping agent work.

The selected scope states its first and last event IDs, event count and captured history/omission limits. All views, agents and filters share that scope. Later tool results, steering, aborts and new requests do not extend it or change its counts. Reopening is an explicit new capture; changing the select chooses from the already captured ranges.

The recap separates these observations:

- **Observed counts** use `summarize` unchanged: model-turn groups, distinct source/call tool and hook identities, individual skill loads, and unlinked boundaries. Start/result pairs count once. A retained completion can count without its start. Every nonzero count exposes its original contributor records, including their recorded source. Counts agree with Statistics on exactly these entries; sums across intervals need not agree with the full window because a call can cross an interval boundary.
- **Information gathering** reuses the retrieval ledger’s supported request contracts and returned/empty/failed/missing/unavailable states. Recognition requires usable source/call/event identities, unique event IDs, ordered complete boundaries without protected omissions, and no unsupported provider metadata on either boundary. Rejected groups keep their original links but leave requested/returned extent unknown; validated shortening facts remain separate. The recap shows literal requested arguments for recognized requests. Unclassified calls may conceal retrieval. A recognized request or returned text does not establish resource coverage, understanding or use.
- **Reported failures** distinguish tool protocol failure records, hook pipeline failure records, host error records and delegated failure records. Interruptions have their own row; warnings are not counted as failures. A complete standalone result may report its own failure without implying a matched start. Clipped, conflicting or protected-omission result evidence cannot supply a protocol status. These are record counts, not counts of failed tasks.
- **Validation observations** reuse the validation overview’s strict literal-command and typed-exit rules. Each recognized request links its original request and compatible result. Tool protocol success, typed process exit, unknown assertions, skipped counts and coverage stay separate. Exit zero does not verify a suite or task. Unclassified calls and missing results remain unknown; Trace runs no checks.
- **Assistant claims** reuse the limited exact-message recognition from claim evidence: `Tests`, `Build` or `Checks` followed by `passed.` or `failed.`. They link the assistant records and remain separate from results. Broader prose is unclassified; no supporting result is inferred.

Scope and limits disclose retained-history limits, Trace clipping and possible host shortening. A zero means no matching observation in the selected range, never proof that nothing happened outside it. No durations are summed, no completion or causal narrative is generated, and overall task success remains unknown.

Each original link requires a unique current event with the complete captured projection unchanged. Eviction, duplication or replacement leaves the frozen recap intact and marks affected links unavailable. Unavailability remains until a new selection or capture. An available original link closes the dialog, pauses Follow/playback, restores Everything in chronological order and opens the raw evidence. Other live updates preserve controls, focus and reading position without a live announcement stream.

Replay, prediction and synthetic examples use only their currently displayed prefix. Entering or leaving these modes and stepping backward closes and clears the recap; detached buttons cannot act in a new capture, even with identical event IDs. Native close events clear ordinary closed dialogs, and each successful open clears prior state before capturing, including when an earlier native close event is still queued.

Disposable helper and DOM fixtures cover same-scope counts, completion-only and repeated calls, overlapping sources, queued prompt context, unknown validation, literal Unicode, empty/partial/clipped ranges, live arrivals, interruption/new-request boundaries, stale navigation, close/reopen races, same-ID mode collisions and reversed prefixes. These checks do not establish rendered geometry or native accessibility.
