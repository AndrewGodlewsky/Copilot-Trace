# Tool outcomes and task outcomes

“Understand this step” uses the existing optional result details to explain what a supported operation reports. It does not judge the requested task. The original recorded event, including literal returned output, remains inspectable in “Recorded evidence.” The shared Tool glossary gives the general read/edit/process distinction.

| Retained evidence | Authored explanation |
| --- | --- |
| Successful `view` or `web_fetch` request with supported arguments and a text result | The operation reports returned data. Relevance, usefulness and sufficiency remain unknown. |
| Successful `edit` or `create` request with supported arguments and a text result | The operation reports a change. Correctness and the overall task outcome remain unknown. |
| Supported ordinary `powershell` request and a unique valid typed `shell_exit` result | Tool protocol success/failure and the numeric process exit are separate. Zero or nonzero describes this command only. Assertions, coverage and task correctness remain unknown. |
| Missing, unsupported or ambiguous contract evidence | The existing neutral event explanation remains. A tool name or successful protocol flag cannot supply an operation-specific meaning. |

The result explanation map is computed once per rendered snapshot, before card reconciliation. It reuses the authored operation contracts, matching tool-call buckets and typed exit parser. The existing validation-command contract is also accepted for its supported request options. Arbitrary supported PowerShell command text stays opaque: the process explanation does not require a recognized validation command or interpret its effects. Output prose such as `PASS` or failing assertions never supplies typed process status or authoritative assertion counts.

Specific explanations require one retained start and result with exact source/call identity, unique usable event IDs, matching raw/projected identities and success fields, and start-before-result order. Both boundaries must have complete unclipped evidence, no protected-content omission and no malformed omission marker. Unknown argument fields, MCP/provider/override markers on either boundary, recorded error fields and contradictory process statuses keep the neutral fallback. A requested shell ID must match the typed exit’s shell ID. Supported names and schemas do not verify native implementation or provider origin; the explanation states this limitation.

The result’s “Inspect validation observations (all retained)” button opens the existing Statistics validation overview. It includes all retained recognized validation attempts across filters and views, with original request/result links and literal output. It does not associate those checks with the selected read or edit. Missing checks mean validation is unknown; the button runs nothing. The separate assistant-claim feature retains its explicit user-link semantics and does not become a correctness verdict.

Opening the overview pauses Follow, focuses its summary and scrolls within the Statistics panel. The scroll position uses the summary’s viewport position, the drawer border and the measured sticky-header height, with room for the focus outline; it does not rely on a nested element’s offset or move the timeline. Closing restores the opener when it remains available. Live updates reuse unchanged controls; changed/evicted result records and page closure invalidate old buttons. A same-ID event whose type changes gets a new row, so obsolete type-specific badges and controls cannot survive. No model calls, commands, file reads, persistence or new host fields are introduced.

Automated coverage uses disposable projected events and the existing DOM boundary double. It covers successful edit without tests, irrelevant read data, zero and nonzero process exits with misleading output prose, opaque commands, unknown/MCP contracts, partial/protected/malformed evidence, independent source identities, literal Unicode/markup, all retained validation navigation, live focus/scroll/Follow preservation, and stale-button rejection. Native wording comprehension, narrow/short panes, enlarged text, keyboard geometry and live desktop reading require owner acceptance; DOM fixtures do not establish those results.
